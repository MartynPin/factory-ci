# Модель прав и секретов

Основание: решения Шагов 6, 13, 14 аудита, находки A-13, A-15, предохранители
v2. Принято 2026-09-06 при постройке Шага 2.

Среда: **личный аккаунт GitHub, тариф Pro.**

**Pro здесь не удобство, а условие работы модели.** Проверено на практике
2026-09-06: `bootstrap.sh` на приватном репозитории тарифа Free получает
`403 Upgrade to GitHub Pro or make this repository public`. Без branch
protection не работают три предохранителя из пяти — запрет прямого push в
`main`, обязательная проверка `verdict` и требование апрува, — и единственным
барьером остаётся ограниченный токен агента.

Альтернатива без оплаты: публичные репозитории, где защита бесплатна. Для
одноразового полигона это приемлемо, для боевых продуктов означает открытый код
и отдельную осторожность с секретами на форках.

`bootstrap.sh` выясняет это **до** первого изменения (шаг 0) и останавливается,
а не падает посередине: половина применённых правил выглядит как работающая
защита, и это опаснее её явного отсутствия. Флаг `--no-protection` позволяет
продолжить сознательно.

---

## Принцип

**Агент не получает ни одного права, которое ему не нужно для следующего
действия.** Не «на всякий случай», не «чтобы не мешало». Каждое право — это
то, что фабрика сможет сделать с собой ночью, когда никто не смотрит.

Три контура, три уровня прав:

| Контур | Что там | Права агента |
|---|---|---|
| `factory-ci` | Определения гейтов | **нет никаких** |
| `factory-knowledge` | Стандарты, промпты, шаблоны, уроки | **нет никаких** |
| Продуктовые репозитории | Код продуктов | push в `task/*`, открытие PR |

Агент не может изменить ни правила, по которым его проверяют, ни знания, по
которым он работает. Это не про недоверие к модели — это про то, что система,
способная переписать свои проверки, перестаёт быть проверяемой.

---

## Решение: fine-grained PAT, не GitHub App

**Выбрано:** отдельный fine-grained personal access token для агента.

**Права токена агента:**

| Область | Право | Зачем |
|---|---|---|
| Только продуктовые репозитории (перечислены поимённо, не «все») | Contents: **Read and write** | push в ветку `task/*` |
| Те же | Pull requests: **Read and write** | открыть PR, писать в описание |
| Те же | Issues: **Read** | прочитать задачу |
| Everything else | **No access** | — |

**Чего у токена нет и не будет:** Administration, Actions, Secrets, Workflows,
Environments, Members.

### Проверено прогоном 2026-09-07

| Действие | Результат |
|---|---|
| Чтение `probe` | успех — контрольная проверка |
| Запись в `main` | отказ 409, защита ветки |
| Запись в `factory-ci` | отказ 403 |
| Правка `.github/workflows/**` | **отказ 403** — `Workflows: No access` работает |
| Создание Issue | **создан, вопреки `Issues: Read-only` и даже `No access`** |

### Ограничение платформы: A-23 правами не закрывается

`Pull requests: Read and write` — без него агент не откроет PR — **включает
доступ к `POST /repos/*/issues`**: GitHub считает pull request разновидностью
issue. Эти два права не разделяются ни при какой комбинации настроек.
Проверено дважды, в том числе при `Issues: No access`.

Вторая половина той же проблемы: fine-grained PAT действует **от имени
владельца**. В созданном Issue стоит `"author_association": "OWNER"`, то есть
действия агента неотличимы от действий человека, и правило «закрывать задачи,
заведённые агентом» реализовать не на чем.

**Следствие:** запрет заменяется обнаружением. Утренняя сводка обязана
перечислять Issues, созданные за период, с указанием авторства. Подробно —
`factory-knowledge/lessons/L-006`. Отдельно про **Workflows: No access** — без этого права
агент не может изменить ни один файл в `.github/workflows/`, даже в
продуктовом репозитории, где у него есть Contents: write. Это механическая
половина гейта «дифф защищённых путей»: гейт ловит попытку, а отсутствие права
делает её невозможной.

**Почему не GitHub App.** App даёт короткоживущие токены и независимость от
личности владельца — оба свойства ценные. Но на личном аккаунте с одним
владельцем App добавляет управление приватным ключом и обменом JWT, не давая
взамен ничего, чего не даёт PAT с тем же набором прав. Агент сейчас работает
локально на машине владельца, а не в облаке.

**Условие пересмотра (расширено 2026-09-07):** переход на GitHub App
выполняется при любом из трёх событий:

1. агент начинает работать на арендованном сервере — ключ перестаёт лежать на
   машине владельца;
2. появляется второй человек с доступом;
3. **фабрика переходит к автономной ночной работе (Шаг 4).**

Третий пункт добавлен по итогам проверки токена: у App собственная личность
(`app[bot]`), поэтому его действия отличимы от действий человека, а права
Issues и Pull requests у App разделены. Это **гипотеза, требующая проверки тем
же прогоном из пяти пунктов** — предыдущее рассуждение о правах звучало столь
же правдоподобно и оказалось неверным.

## Секреты: агент их не видит вообще

Секреты живут в **environments**, а не в секретах репозитория.

| Environment | Что хранит | Кто может использовать |
|---|---|---|
| `production` | Ключи деплоя, боевой `DATABASE_URL` | Только workflow деплоя, только с ветки `main`, только после ручного апрува владельца |
| (без environment) | ничего | Все джобы гейтов |

Джобы, которые запускают проверки на коде из PR, **не объявляют environment**.
Технически это означает, что секретов в их окружении нет — не «есть, но не
используются», а нет.

Это же закрывает разделение из решения Шага 13: джоба, видящая код PR, и
джоба, имеющая доступ к секретам, — разные джобы, и вторая недостижима из
первой.

## Права `GITHUB_TOKEN` в самих workflow

По умолчанию в каждом workflow:

```yaml
permissions: {}
```

Пустой набор, и каждая джоба добавляет себе ровно то, что ей нужно. Это
противоположность настройке по умолчанию, где токен получает write почти на всё.

| Джоба | permissions |
|---|---|
| Предполёт, гейты, проверка диффа | `contents: read` |
| Публикация вердикта в PR | `pull-requests: write` |
| Мердж-бот | `contents: write`, `pull-requests: write` |
| Деплой | `contents: read`, `deployments: write` |

---

## Права при вызове reusable workflow — это верхняя граница

`permissions: {}` на верхнем уровне вызывающего workflow означает «никаких прав
вообще». Вызываемый workflow **не может запросить больше, чем дал вызывающий**:
если `gates.yml` просит `contents: read`, а вызывающий не дал ничего, GitHub
отклоняет запуск на этапе разбора — прогон падает за 0 секунд с формулировкой
«This run likely failed because of a workflow file issue», не создав ни одной
джобы, и `gh pr checks` показывает пустоту.

Поэтому права объявляются **на уровне джобы вызова**:

```yaml
permissions: {}          # по умолчанию — ничего

jobs:
  gates:
    permissions:         # верхняя граница для вызываемого workflow
      contents: read
      pull-requests: write
    uses: OWNER/factory-ci/.github/workflows/gates.yml@<SHA>
```

Проверено на практике 2026-09-06: три прогона подряд падали за 0 секунд именно
по этой причине. `actionlint` файл `gates.yml` считает корректным — ошибка не в
нём, а в отношении между двумя файлами, и никакой линтер её не ловит.

Побочная проверка: `factory-ci` был сделан публичным по подозрению, что
приватный репозиторий не может быть вызван публичным. Подозрение **не
подтвердилось** — падение продолжалось. Видимость репозиториев к этому
отношения не имеет.

## Защита `main` живёт вне git — и потому проверяется

Находка A-13: branch protection не является частью репозитория. Её нельзя
посмотреть в диффе, она не восстанавливается из истории, и её отключение не
оставляет следа в коде.

Поэтому:

1. `setup/bootstrap.sh` применяет защиту через API — один раз при создании
   репозитория;
2. `setup/verify.sh` **проверяет фактическое состояние защиты** и печатает
   расхождения с ожидаемым;
3. `verify.sh` запускается еженедельным workflow, и его провал попадает в
   утреннюю сводку.

Настройка, которую никто не проверяет, — это настройка, которой нет.

### Что именно защищено на `main`

- Прямой push запрещён всем, включая владельца.
- Обязательная проверка — **ровно одна: `verdict`** (см. ниже).
- Обязателен апрув: 1 ревьюер.
- История линейная, force-push и удаление ветки запрещены.

---

## Один обязательный чек, а не двенадцать

Решение аудита прямо запрещает условия `if:` в обязательных джобах: **GitHub
засчитывает `skipped` как успех.** Джоба, пропущенная по условию, выглядит для
branch protection так же, как пройденная.

Поэтому обязательной проверкой объявляется **одна** джоба — `verdict`. Она:

- запускается **всегда** (`if: always()`), без единого условия;
- собирает результаты всех остальных джоб через `needs`;
- падает, если хоть одна не в состоянии `success`;
- падает и при `env_fail`, но с другим сообщением и меткой на PR.

Так список гейтов можно менять, не трогая настройки защиты ветки, и ни одна
пропущенная джоба не пролезет как успешная.

---

## Три состояния гейта в терминах GitHub

У GitHub нет третьего статуса, поэтому `env_fail` кодируется иначе:

| Ситуация | Что видит GitHub | Что видит конвейер |
|---|---|---|
| Всё зелено | `verdict` = success | мердж возможен |
| Провал работы | `verdict` = failure, метки нет | попытка засчитана |
| Отказ окружения | `verdict` = failure, **метка `env_fail`** | попытка НЕ засчитана, ретрай не запускается |

PR блокируется в обоих случаях провала — это правильно, сломанное окружение
не повод мерджить. Но метка отличает «агент не справился» от «инструмент
сломан», и именно она управляет решением о ретрае.

---

## Мердж выполняет код, а не агент

У агента нет права на мердж — ни через токен, ни через настройки. Мердж делает
отдельный workflow, срабатывающий по метке `approved`, которую ставит владелец.

Мердж-бот перед слиянием ещё раз проверяет, что `verdict` в состоянии success
на **текущем** SHA. Это защита от гонки: апрув мог быть поставлен до
последнего push.

## Reusable workflows вызываются по SHA, не по ветке

```yaml
uses: OWNER/factory-ci/.github/workflows/gates.yml@<полный 40-символьный SHA>
```

Ссылка на `@main` означает, что изменение в `factory-ci` немедленно меняет
проверки во всех продуктовых репозиториях — включая те PR, что уже открыты.
Обновление SHA — отдельный PR в продуктовом репозитории, видимый в диффе.

**Требуется настройка:** приватный `factory-ci` по умолчанию недоступен другим
репозиториям. `bootstrap.sh` открывает доступ на уровне владельца
(`access_level=user`).
